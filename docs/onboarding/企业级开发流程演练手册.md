## 幕 1 · 立规矩（第一个 PR）

这一幕你会干两件事：改 CODEOWNERS 里的占位符（**用 PR 改，不直接 push**），以及开启分支保护。

### 1.1 改 CODEOWNERS 走 PR 流程

```bash
git checkout develop
git pull
git checkout -b chore/set-codeowners
```

用编辑器把 `.github/CODEOWNERS` 里所有 `@YOUR_GITHUB_USERNAME` 改成你的真实用户名（例如 `@ray-cn`），然后：

```bash
git add .github/CODEOWNERS
git commit -m "chore(codeowners): 替换为真实仓库负责人"
git push -u origin chore/set-codeowners
```

然后打开 https://github.com/<你的用户名>/ecom-ai-cs/compare/develop...chore/set-codeowners ，
点 **Create pull request**，标题填 `chore(codeowners): 替换为真实仓库负责人`，描述里写：

```
把 CODEOWNERS 占位符替换为实际负责人，否则核心模块评审规则不生效。
影响范围：仅仓库配置，无业务代码改动。
```

点 **Create pull request** → 等 CI 跑完（约 1 分钟，页面底部出现绿色 ✓）→ 点 **Squash and merge** → **Confirm** → 点 **Delete branch**。

本地同步：

```bash
git checkout develop && git pull && git branch -d chore/set-codeowners
```

### 1.2 开启分支保护（这是"规矩"真正生效的地方）

打开 `https://github.com/<你的用户名>/ecom-ai-cs/settings/branches` → **Add branch protection rule**：

**规则一：保护 main**

| 配置项 | 值 |
|--------|-----|
| Branch name pattern | `main` |
| Require a pull request before merging | ✅ 勾选 |
| Require approvals | 1（想单人演练可先填 0，见幕 8 说明） |
| Require status checks to pass | ✅ 勾选，然后搜索并选中 `单元测试与评测`、`PR 标题规范检查` |
| Require conversation resolution before merging | ✅ 勾选（评论必须点 Resolve 才能合） |
| Do not allow bypassing the above settings | ✅ 勾选（管理员也不能绕） |
| Allow force pushes | ❌ 不勾 |

**规则二：保护 develop** —— 同上一套，`Require approvals` 填 0（自己开发自己合，但 CI 必须绿）。

同时到 `Settings → Actions → General`，确认 **Allow all actions and reusable workflows** 已选中。

### 预期看到什么

- 规则建好后，你尝试 `git push origin main` 直接推一个空提交，会被拒绝：

```
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
```

**看到这条报错就是成功了** —— 这是企业里"分支被锁住"的真实体感。

### 为什么企业要这么做

分支保护把"靠自觉"变成"靠系统"。没有它，任何人一条 `git push -f` 就能覆盖线上代码；有了它，代码只能从 PR 进来，且必须过 CI 和评审——**规矩不依赖人的品格，依赖配置**。

## 幕 3 · 开工（拉分支 + 写代码）

### 3.1 拉分支

```bash
git checkout develop
git pull
git checkout -b feature/followup-suggest
```

**判断标准**：`git branch` 里当前分支前面有 `*`，且名字是 `feature/followup-suggest`。

### 3.2 写代码（三步改动）

**改动 1：新建 `src/ecom_cs/suggestions.py`**

```python
"""追问推荐：回答后引导用户继续提问。

硬性要求（PRD 验收标准第 4 条）：每条推荐都必须是本系统能正确识别的问法，
否则用户点了一下反而得到"转人工"，体验比没有推荐更差。
"""

from __future__ import annotations

from .intent import LOGISTICS, ORDER, REFUND

# 每个意图对应的推荐问法
_SUGGESTIONS: dict[str, list[str]] = {
    LOGISTICS: ["退款多久到账", "物流不更新怎么办", "发票怎么开"],
    ORDER: ["我的快递到哪了", "退款多久到账", "发票怎么开"],
    REFUND: ["退款多久到账", "发票怎么开", "我的订单到哪了"],
}

MAX_SUGGESTIONS = 3


def suggest(intent: str) -> list[str]:
    """返回该意图下的推荐追问，最多 3 条；无匹配时返回空列表。"""
    return list(_SUGGESTIONS.get(intent, []))[:MAX_SUGGESTIONS]
```

**改动 2：修改 `src/ecom_cs/service.py`**

第一处，导入区加一行：

```python
from .suggestions import suggest
```

第二处，把 `_reply` 函数改成带 `suggestions` 参数的版本：

```python
def _reply(
    text: str,
    intent: str,
    *,
    transfer_to_human: bool = False,
    sources: list[str] | None = None,
    action: str = "answer",
) -> dict[str, Any]:
    # 转人工与追问订单号时不推荐，避免用户被引到别的话题
    followups = [] if transfer_to_human or action != "answer" else suggest(intent)
    return {
        "reply": text,
        "intent": intent,
        "need_human": transfer_to_human,
        "sources": sources or [],
        "action": action,
        "suggestions": followups,
    }
```

**改动 3：新建 `tests/test_suggestions.py`**

```python
"""追问推荐测试：数量、相关性、以及"点了能答"的闭环校验。"""

from ecom_cs.intent import LOGISTICS, OTHER, REFUND
from ecom_cs.service import handle
from ecom_cs.suggestions import MAX_SUGGESTIONS, suggest


class TestSuggest:
    def test_logistics_intent_returns_at_most_three(self):
        items = suggest(LOGISTICS)
        assert 1 <= len(items) <= MAX_SUGGESTIONS

    def test_other_intent_returns_empty(self):
        assert suggest(OTHER) == []

    def test_every_suggestion_can_be_answered(self):
        # 闭环校验：推荐的话术点下去必须能得到答案，而不是被转人工
        # 判定标准是"不需要转人工"，而不是"检测出某个意图"——
        # 像"发票怎么开"这类问题意图是 other，但知识库能答，同样算闭环。
        for intent in (LOGISTICS, REFUND):
            for item in suggest(intent):
                result = handle(item)
                assert result["need_human"] is False, f"推荐语点了答不上：{item}"


class TestServiceIntegration:
    def test_answer_carries_suggestions(self):
        result = handle("双11买的衣服7天无理由退货吗？")
        assert result["suggestions"]
        assert len(result["suggestions"]) <= 3

    def test_transfer_to_human_has_no_suggestions(self):
        result = handle("你们老板是谁")
        assert result["need_human"] is True
        assert result["suggestions"] == []
```

> **踩坑提示（我实测时踩过）**：第一版写的是 `assert detect_intent(item) != OTHER`，
> 结果 `发票怎么开` 直接失败——它在规则引擎里意图就是 `other`，但知识库能正常回答。
> 这说明**验收标准要用"用户视角"表述**（点了有没有答案），而不是用内部实现细节（识别出什么意图）。
> 若按实现写测试，你会误删一条本来好用的推荐。

### 为什么企业要这么做

- 新建文件而不是把逻辑塞进 `service.py`：模块单一职责，评审时改动范围一目了然
- 测试里那条 `test_every_suggestion_is_recognizable` 是把 PRD 的验收标准**变成代码**
- 分支名 `feature/followup-suggest` 让任何人看分支列表就知道在做什么

### 卡住了怎么办

- 改完启动报 `ModuleNotFoundError: ecom_cs` → 用 `python chat.py "..."` 或 `pytest`（已配 `pythonpath=src`），别用 `python -m ecom_cs.cli`

## 幕 7 · CI 红灯演练（故意弄红一次，你才懂绿灯的价值）

### 7.1 制造失败

打开 `tests/test_suggestions.py`，把这一行故意改错：

```python
    def test_logistics_intent_returns_at_most_three(self):
        items = suggest(LOGISTICS)
        assert 1 <= len(items) <= 2      # 故意写错：实际返回 3 条，应为 3
```

```bash
git add tests/test_suggestions.py
git commit -m "test(suggestions): 调整断言（演练：故意制造失败）"
git push
```

### 7.2 去 Actions 看红灯

打开 `https://github.com/<你的用户名>/ecom-ai-cs/actions`，点最新那次运行 → 点 `单元测试与评测` → 展开 `单元测试 + 覆盖率` 步骤，会看到：

```
FAILED tests/test_suggestions.py::TestSuggest::test_logistics_intent_returns_at_most_three
AssertionError: assert 3 <= 2
1 failed, 22 passed
```

PR 页面顶部同时出现红叉，合并按钮变灰。

### 7.3 修绿

把断言改回 `<= 3`，然后：

```bash
git add tests/test_suggestions.py
git commit -m "test(suggestions): 修正断言上限为 3"
git push
```

再看 Actions → 绿色 ✓ → PR 页面提示 "All checks have passed"。

### 为什么企业要这么做

CI 的价值是**把"我以为没问题"换成机器判断**。你刚体验的这 3 分钟，就是企业里每天发生几十次的事：红灯 → 本机复现 → 修 → 推 → 绿灯。等红灯时不要去找人求放行，那是把自己的人品押上去；修绿才是唯一正解。

### 卡住了怎么办

- Actions 没触发 → 检查 `Settings → Actions → General` 是否允许，以及 workflow 文件里 `on:` 是否包含 `pull_request`
- 报 `pip install` 慢 → 正常，首次约 1 分钟，有 cache 后变快

## 幕 8 · 评审（你被"挑刺"，然后体面地改）

### 8.1 先解决一个现实问题：你只有一个人

企业里"至少 1 人批准"需要第二个账号。三种做法，按真实度排序：

**方案 A（推荐）**：注册/使用第二个 GitHub 账号 → 仓库 `Settings → Collaborators → Add people` 加进来 → 用浏览器**无痕窗口**登录小号打开你的 PR → 用"Review changes"提交评审意见。这样你能完整走一遍"作者 vs 评审人"的双向体验。

**方案 B**：拉一位同事/朋友作为 collaborator，让他真实评审。

**方案 C（最低成本）**：把分支保护的 `Require approvals` 设为 0，自己按下面的清单在 PR 里逐条留评论再 Resolve——动作是真的，只是少了他人把关。

### 8.2 评审人会这么说（真实话术）

在 PR 的 Files changed 页面，对 `src/ecom_cs/service.py` 的 `_reply` 那几行发表评论：

```
[blocking] 转人工时 suggestions 为空是对的，但"ask_order_id" 场景也返回空，
用户刚被问订单号、正需要引导，这里应该给 1-2 条相关推荐，否则体验断档。
```

再对 `suggestions.py` 评论一条：

```
[suggestion] 建议把推荐话术常量提到文件顶部并加注释说明"必须可被 detect_intent 识别"，
否则后人加一条识别不了的话术，验收标准 4 就悄悄失效了。
```

### 8.3 你要怎么回应（企业礼仪 + 技术判断）

1. **不要沉默**，每条 review 都要回一句：改了就写"已修改，见 commit xxx"；不改就说明理由
2. `[blocking]` 必须改，除非你能给出更强理由并说服对方
3. `[suggestion]` 可以讨论，但要明确表态（采纳/不采纳 + 原因）
4. 改完点 **Resolve conversation**，然后 `git push` 新提交（PR 会自动更新）

**这次我们采纳 [suggestion]（真有用），部分采纳 [blocking]**：ask_order_id 场景加上推荐，但只给 1 条（避免追问订单号时信息过载）。

改 `service.py` 的 `_reply`：

```python
    # 转人工时不推荐；追问订单号时只给 1 条，避免信息过载
    if transfer_to_human:
        followups: list[str] = []
    elif action == "ask_order_id":
        followups = suggest(intent)[:1]
    else:
        followups = suggest(intent)
```

```bash
pytest -q
git add src/ecom_cs/service.py
git commit -m "refactor(chat): 追问订单号场景保留 1 条推荐

评审意见 #1：ask_order_id 场景不应完全无引导"
git push
```

### 预期看到什么

PR 页面出现新的提交、CI 重新跑、评论被标记 Resolved。若你设了 approvals 且有第二人，点 **Approve** 后合并按钮才变绿。

### 为什么企业要这么做

评审不是为了挑错，是为了**让代码在离开你脑子之前，先经过另一个人的脑子**。规则里 `[blocking]/[suggestion]/[nit]` 这三档，就是让"必须改"和"随便说说"分开，避免作者把每条意见都当圣旨，也避免评审人用"我觉得"卡人。

## 幕 9 · 合并（把 N 次提交压成 1 条干净历史）

PR 页面底部，合并按钮旁的下拉箭头 → 选 **Squash and merge** → 点按钮 → 确认弹窗里把提交信息整理成：

```
feat(chat): 回答后推荐 3 个相关追问 (#2)
```

→ **Confirm squash and merge** → 点 **Delete branch**。

回本地收尾：

```bash
git checkout develop
git pull
git branch -d feature/followup-suggest
git log --oneline -3
```

预期：

```
b2c3d4e feat(chat): 回答后推荐 3 个相关追问 (#2)
21ee0c0 docs: 补充架构决策、PRD 与值班手册
```

> 注意：你原来那 4 次提交（含"故意制造失败"那次）在 develop 上只剩 **1 条**——这就是 Squash。主分支历史永远是"一条需求一条记录"，而不是"作者的思考过程"。

同时打开 Issue #1，它会因为 `Closes #1` **自动关闭**，状态显示 Closed。

### 为什么企业要这么做

- Squash：主干历史可读，回滚一个功能就是回滚一个提交
- 合并后删分支：分支列表只剩活跃分支，避免"300 条陈年分支"
- `Closes #1` 自动关单：需求和代码自动对上账，不用人去点

## 幕 11 · 线上救火（hotfix 通道，S0 故障）

### 11.1 事故报告（模拟）

> **周五 20:10 商家群反馈**：用户说"东西到货就坏了，我要退款"，机器人回答"退货签收后 1-3 个工作日原路退回"，完全没提售后处理，用户直接投诉。
> 影响：质量问题投诉被当成普通退款咨询，涉及所有使用 AI 客服的商家。
> 定级：**S0**（商业影响 + 全量商家）。

先在 Issue 里建一张 Bug 卡（用 Bug 模板）：

```
标题：【Bug】质量投诉被当成普通退款，未转人工
严重程度：S0 线上不可用（走 hotfix 通道）
复现步骤：1. 打开客服窗口 2. 输入"东西到货就坏了，我要退款" 3. 观察回答
期望：识别为质量投诉，立即转人工
实际：回答退款到账时效，未转人工
环境与版本：生产 v0.2.0
```

假设编号是 **#3**。

### 11.2 本地先复现（救火第一原则：先看见，再动手）

```bash
cd "C:/Users/Administrator/WorkBuddy/电商团队开发/ecom-ai-cs"
git checkout main && git pull
python chat.py "东西到货就坏了，我要退款"
```

```
机器人：退货签收后 1-3 个工作日原路退回，银行卡到账可能再延迟 1-2 天。
详情：意图=refund 转人工=False 引用=['refund-process']
```

### 11.3 从 main 拉 hotfix 分支（注意：不是 develop）

```bash
git checkout -b hotfix/v0.2.1-quality-complaint
```

改 `src/ecom_cs/service.py`，在 `handle` 开头、意图分支之前插入质量投诉判定：

```python
# 质量/破损类投诉必须人工介入：涉及赔偿，AI 不允许承诺任何方案
QUALITY_COMPLAINT_KEYWORDS = ("坏了", "破损", "质量问题", "漏发", "发霉", "过敏")
```

```python
    # 最高优先级：质量投诉一律转人工，不允许用退款政策话术敷衍
    if any(word in text for word in QUALITY_COMPLAINT_KEYWORDS):
        return _reply(TRANSFER_TEXT, intent, transfer_to_human=True, action="transfer_human")
```

补一条回归测试（钉死这个 Bug，永不再犯）：

```python
# tests/test_service.py 末尾追加
class TestQualityComplaint:
    def test_damaged_item_goes_to_human(self):
        result = handle("东西到货就坏了，我要退款")
        assert result["need_human"] is True
        assert result["action"] == "transfer_human"
```

### 11.4 提交并发 PR 到 main

```bash
git add src/ecom_cs/service.py tests/test_service.py
git commit -m "fix(chat): 质量投诉强制转人工，禁止套用退款政策话术

线上 S0：用户反馈商品损坏时，AI 只答退款时效未转人工。

```

开 PR，**base 选 main**，标题 `fix(chat): 质量投诉强制转人工`，描述写明影响面、回滚方式（"回滚到 v0.2.0"）、验证结果。CI 绿 + 评审通过后，合并方式选 **Merge commit**（hotfix 保留原提交，便于追溯）。

### 11.5 打补丁版本并发布

```bash
git checkout main && git pull
git tag -a v0.2.1 -m "v0.2.1 修复质量投诉未转人工（S0）"
git push origin v0.2.1
```

在 Releases 页面发布 v0.2.1，说明里写清"修复内容 + 影响范围 + 回滚方式"。

### 11.6 最关键的一步：合回 develop（90% 的新人会忘）

```bash
git checkout develop
git pull
git merge main
git push
```

**为什么必须做**：develop 上还在往下开发 v0.3.0，如果补丁只在 main 上，下次发版从 develop 出包时，`service.py` 又变回没有质量投诉判定的老版本——**Bug 复活，而且没人知道为什么**。

### 为什么企业要这么做

- hotfix 从 main 拉：基于线上真实状态修，不夹带 develop 上未发布的功能
- 只改一个 Bug：插队通道越干净，回滚越容易
- 双写 main + develop：这是"修好了"和"以后不再坏"的区别

### 卡住了怎么办

- main 有保护规则推不上去 → 正常，hotfix 也必须走 PR（这就是规矩）
- 合并冲突 → 因为 main 和 develop 分叉了，手动解冲突后 `git add` + `git commit`
