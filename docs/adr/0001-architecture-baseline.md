# ADR-0001 技术选型基线

- 状态：已接受
- 日期：2026-11-10
- 决策人：架构组
- 影响范围：全项目

## 背景

电商 AI 客服需要在 16 周内上线首个商业版本，团队 8 人，其中后端 2 人、算法 1 人。
需要先确定：语言与框架、意图识别方案、知识库召回方案。

## 决策

1. **语言与框架**：Python 3.10+，服务层用 FastAPI（当前仓库先用纯标准库实现核心逻辑，便于测试与替换）
2. **意图识别**：规则/关键词优先，保留 `detect_intent(text) -> str` 接口，后续替换为大模型分类器
3. **知识召回**：先做关键词打分占位，接口形态与向量检索一致（`search(text) -> [(知识, 分数)]`），后续换 Milvus + Embedding 不影响上层编排
4. **兜底策略**：任何不确定场景一律转人工，禁止"猜一个答案"

## 理由

- 规则优先可以零成本上线、可解释、可单测，先用它把"转人工"这条商业红线跑通
- 接口先行，算法侧的演进（规则 → 小模型 → 大模型）不需要改动对话编排
- 先做最小闭环再加厚，符合 16 周里程碑里 W3-6 出 MVP 的要求

## 后果

- 早期回答覆盖率有限，转人工率会偏高（可接受，灰度期人工坐席旁听）
- 规则维护成本随场景增多而上升，需在第 2 阶段引入分类模型
- 关键词召回对同义表达不鲁棒（如"多久能到"与"几天到"），必须在评测集里覆盖

## 备选方案与未采纳原因

| 方案 | 未采纳原因 |
|------|-----------|
| 直接上大模型端到端生成 | 幻觉不可控，政策类问题（退货、赔偿）风险高，且成本不可预估 |
| 全流程 Java | 算法生态弱，评测与实验迭代慢 |
| 微服务拆分 | 8 人团队过早拆分，运维成本压不住 |
